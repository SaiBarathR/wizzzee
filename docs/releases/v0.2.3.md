# Wizzzee 0.2.3

Wizzzee is a disk space analyzer for macOS in the shape of
[WizTree](https://diskanalyzer.com/): a folder tree with sizes, a list of the
biggest files, and a colored treemap you can click into. It scans a full startup
disk — around 3.9 million files — in roughly 15 seconds.

**This one is worth upgrading to.** 0.2.2 could report an empty scan for a folder
that was not empty, and could act on the wrong file after a delete. Both are
fixed here.

## Scanning a symlinked folder reported nothing

Scanning `/tmp`, `/etc`, `/var` — or any folder that is itself a symlink — printed
"Scan complete" with **zero bytes and zero files**, and marked one directory
unreadable. The same thing happened for `/private/tmp` and friends, which look
like ordinary directories.

Wizzzee opens directories in a way that deliberately refuses to follow symlinks,
so a link cannot smuggle another part of the disk into the totals. That is right
for everything *inside* a scan, but it also refused the folder you actually asked
for. Scan roots are resolved to their real location first now.

A tool for measuring disks silently reporting nothing is the worst way for it to
be wrong, so if you scanned one of those paths on an earlier version, the answer
you got was not real.

## The file list could act on the wrong file after a delete

The File View identifies each row by its position in the folder, so deleting a
file shifted every row after it onto its neighbour. The rows on screen were not
rebuilt until a fresh pass over the scan finished, and in that window:

- double-clicking a row revealed a different file in Finder, and
- deleting a row deleted a different file

with nothing to indicate it had happened. The stale rows are now discarded the
moment a delete lands, and a pass that was already running when the tree changed
is thrown away instead of being shown. Rescanning had the same problem from the
other end and is fixed with it.

## Other fixes

- **A treemap zoomed into a folder whose parent you then deleted** could read
  memory that had been freed, which in the worst case means a delete resolving to
  a path that no longer describes anything.
- **`/usr/local` is protected correctly.** The check that exempts it from the
  read-only system volume matched on text rather than on path components, so a
  folder merely starting with those letters — `/usr/locality` — was offered for
  deletion as though it were not protected.
- **The File View's total agrees with its own columns.** It added up logical size
  while On Disk was the metric selected and the column being sorted by, so the
  figure disagreed with both the rows above it and the status bar below it.
- **Internal:** the scan's shared bookkeeping was restructured to remove a
  concurrency rule violation that had no visible effect but could have become one
  under a future compiler. Scan totals are byte-identical and the timings
  unchanged.

Scan totals were checked byte-for-byte against the previous release, and against
`du`, to confirm none of this changed what Wizzzee measures.

## Reading the numbers

- **On Disk is the default.** Logical size is misleading on macOS, where sparse
  container and VM images routinely report hundreds of gigabytes they do not
  occupy. Space on disk is what deleting something gives back.
- **Base-10 units,** matching Finder and Get Info. This differs from `df -h`,
  which is base-2.
- **Hard links are counted once,** with the amount that would otherwise have been
  double-counted shown in the status bar.
- **One volume per scan.** APFS firmlinks are followed once, so `/Users` is
  counted and `/System/Volumes/Data/Users` — the same directory by another path —
  is not.
- **Totals will not exactly match `df`.** Unreadable folders, APFS snapshots and
  filesystem metadata account for the difference; the header reports how many
  folders could not be read.

## Full Disk Access

Without it, macOS hides Mail, Messages, Safari, Time Machine and other users'
home folders, and the totals read low. The header says so when it detects this.

Grant it in **System Settings → Privacy & Security → Full Disk Access → +**,
adding `Wizzzee.app`.

**Upgrading:** because the app is ad-hoc signed, macOS keys the grant to that
exact binary, so 0.2.3 has to be added to Full Disk Access again. Remove the old
entry and add the new app.

## Compatibility

- Requires macOS 14 or newer.
- Apple Silicon is verified.
- The universal app contains native `arm64` and `x86_64` slices. Intel hardware
  has not been tested, so Intel support is provisional rather than verified.

## Installation

1. Download `Wizzzee-0.2.3-macos-universal.zip` and `SHA256SUMS.txt`.
2. Keep both in the same directory and run `shasum -a 256 -c SHA256SUMS.txt`.
3. Unzip and move `Wizzzee.app` to Applications.
4. Open it once and dismiss the warning, then go to **System Settings → Privacy
   & Security** and click **Open Anyway** next to the message about Wizzzee.

Wizzzee is ad-hoc signed rather than Developer ID signed or notarized, so macOS
requires this one-time Gatekeeper confirmation. On macOS 14 you can instead
Control-click the app and choose **Open** — macOS 15 removed that shortcut for
apps that are not notarized, which earlier release notes and the README did not
account for.

## Verification

After extraction:

```sh
lipo -archs "Wizzzee.app/Contents/MacOS/Wizzzee"
codesign --verify --deep --strict --verbose=2 "Wizzzee.app"
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' "Wizzzee.app/Contents/Info.plist"
```

These should report both `arm64` and `x86_64`, a valid ad-hoc signature, and
version `0.2.3`.

You can also check the build itself:

```sh
"Wizzzee.app/Contents/MacOS/Wizzzee" --selftest
```

That builds a throwaway tree with known contents and verifies the scanner and
both delete paths against ground truth — 88 checks, no permissions needed,
including new ones covering both fixes above. It writes only to a temporary
directory and a throwaway preference suite, both removed afterwards, so running
it leaves no trace and changes no settings.

## Known limitations

- Not notarized, so first launch needs the Gatekeeper confirmation above.
- One volume per scan; other disks and network shares are skipped.
- `/System`, `/usr`, `/bin` and `/sbin` live on the sealed system volume and
  cannot be deleted by anything, including an administrator. Wizzzee still shows
  them so the space is accounted for, and says so rather than failing with a bare
  permission error.
