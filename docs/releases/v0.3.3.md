# Wizzzee 0.3.3

Wizzzee is a disk space analyzer for macOS in the shape of [WizTree](https://diskanalyzer.com/): a folder tree with sizes, a list of the biggest files, and a colored treemap you can click into. It scans a full startup disk — around 3.9 million files — in roughly 15 seconds.

**Upgrade from 0.3.2.** It can crash, or lock up with a spinning cursor, a few clicks after you rescan. That is fixed here, along with a panel that showed stale numbers after a delete. Both were found the day after 0.3.2 shipped, by testing the released app by hand rather than its code.

If you are coming from 0.3.1 or earlier, [0.3.2](https://github.com/SaiBarathR/wizzzee/releases/tag/v0.3.2) is worth reading too: it closed three ways a delete could remove something you had not picked.

## A crash or a freeze after rescanning

Right-click a folder, rescan, then carry on using the app — open another menu, confirm or cancel a delete — and Wizzzee could quit without warning or stop responding at full CPU.

A right-click menu remembers the item it was opened for, and the system keeps that menu around after it has closed. Once you rescan, the item belongs to a scan that no longer exists. Wizzzee went on asking that leftover menu whether its item could be deleted, and answering meant reading the folders above it — folders that had already been thrown away.

What it read there was down to luck, which is why it looked random. Straight after a rescan the new scan's folders usually sit in the same memory, and nothing visibly went wrong. Some clicks later that memory had been reused for something else, and the app crashed or went round in circles. Three runs through the same steps failed three times: two crashes and one freeze.

A folder now knows when the folders above it are gone, instead of assuming they are still there. A leftover from an old scan is recognised as such and ignored. This is not new in 0.3.2 — it is as old as the right-click menu — and it was the same mistake behind both treemap crashes fixed in 0.3.2. Those were fixed one place at a time; this removes the cause.

## The File Types panel follows a delete

The panel at the right of the tree — each file type with its size, its share and its file count — was worked out once per scan and never again. Delete something and the folder totals dropped, while the panel went on listing the files you had just removed, measured against a total that no longer included them. Delete a 1.5 GB file from a small folder and its type read as **31789.1 %** of the scan.

The panel now changes with the tree: a deleted file comes out of its type, a type with nothing left disappears, and the percentages add up again. It shows exactly what a rescan would.

## Small things

- A folder holding one file was offered for deletion as "… and 1 items inside it?", and a scan of a single file reported "1 files". One of something is now singular wherever it appears.

## Installing

Download `Wizzzee-0.3.3-macos-universal.zip` below, unzip it, and move `Wizzzee.app` to Applications, replacing the old one.

- **First launch.** The app is not notarized, so macOS blocks it the first time. Open it once, dismiss the warning, then go to **System Settings → Privacy & Security** and click **Open Anyway**. macOS asks only once.
- **Full Disk Access has to be granted again.** macOS ties that permission to the exact build, so the grant from an earlier version does not carry over. In **System Settings → Privacy & Security → Full Disk Access**, remove the old Wizzzee entry and add the new app. Without it, Mail, Messages, Safari and other users' folders are skipped and the totals read low.

It runs on macOS 14 or newer, on Apple silicon and Intel.

## Internal

0.3.2 was reviewed line by line, more than once, and passed every automated check. This release exists because none of that used the app. A model was given the released build and a throwaway folder and asked to work through fourteen scenarios by clicking — scan, sort, filter, zoom, delete — and the crash turned up in the tenth.

Reproducing it took longer than fixing it. The obvious short sequences did not fail, even with the system set to scribble over freed memory, because the new scan reuses that memory at once and the scribble is overwritten with something valid. Only the full sequence failed, and it failed every time.

The fix changes how a folder refers to its parent, which every scan creates hundreds of thousands of times, so it was measured: on a folder of 397,000 files and 70,000 subfolders, scan time and peak memory are the same as before to within run-to-run noise.

The self-test grew from 235 checks to 249 and now also runs clean under an address sanitizer, which reports the old fault directly. The fixed build was then put through the failing sequence by hand again, and through the delete scenarios, before this was tagged.
