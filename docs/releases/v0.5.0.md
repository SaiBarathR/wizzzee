# Wizzzee 0.5.0

Wizzzee is a disk space analyzer for macOS in the shape of [WizTree](https://diskanalyzer.com/): a folder tree with sizes, a list of the biggest files, and a colored treemap you can click into. It scans a full startup disk — around 3.9 million files — in roughly 15 seconds.

**This release is about deciding.** Wizzzee could find what was big and remove it safely; the step in between — what is this, where is the rest of it, is it safe to lose — sent you to Finder. You can now look at a file without leaving the app, pick a file type out and see where it lives, search for folders as well as files by size and age, and take a move to the Trash back.

## Look at a file before deciding about it

`⌘Y` opens Quick Look on the selected item, and shuts it again. It is Finder's other key for it — Space, its first, marks a row here — and it is in the File menu and the right-click menu too.

- While it is up it shows the one thing selected. Selecting something else shows that instead, and selecting several rows shuts it.
- Opened from the right-click menu, it selects the row it shows — so `⌘⌫` removes what is in the panel and nothing else.
- When the item on show is removed, the panel moves on to whatever took its place, so a list can be worked down with it up: look, remove, look.
- A folder can be looked at as well as a file.
- A file marked **online only** is not shown. Reading one is what downloads it, and a look at a 4 GB file that was taking no space would put 4 GB on a disk you are in the middle of emptying.

## Pick a file type out, and see where it lives

File Types said how much of a scan a type took and nothing about where. Click a row of it now and:

- on the treemap, every tile of another type is set back — greyed and darkened — so the type shows as lit patches across the disk;
- File View lists that type's largest files and no others;
- a label naming the type (`.dmg only ✕`) appears beside the map and above the file list. Click it to let go, or press `Esc` in the File Types list.

The list also stopped at the forty largest types, with no way to reach the rest. Its heading, `top 40 of N`, is now a button that lists all of them.

## Search for folders, by size and by age

The File View's filter was one piece of text matched against file names. It could not find a folder, and could not be told how big or how old. `⌘F` now goes to it from any tab, and what you type is read:

| You type | It finds |
| --- | --- |
| `node_modules` | every file **and folder** with that in its name |
| `two words` | names with both words in them, in any order; `"two words"` in quotes is one |
| `src/app` | a word with a `/` is looked for in the whole path |
| `>1gb` `<500kb` | what is bigger, or smaller |
| `older:1y` `newer:30d` | by when it was last modified (`d`, `w`, `m`, `y`) |
| `ext:dmg` | one file type; `ext:none` for files with no extension |
| `kind:folder` `kind:file` | folders only, or files only |

They combine: `>1gb older:1y` is every file over a gigabyte that has not been touched in a year. Sizes and ages on their own find files; with a word, or `kind:folder`, folders are found as well. A second filter of a kind narrows the first, as a second word does.

The line at the right now says how many things matched — all of them, not only the thousand listed — and what they take up. A match inside a folder that also matched is counted, and adds nothing to the size, so `node_modules` gives you what all of them come to, once.

A folder that a search turns up is a row like any other: it can be marked, removed, looked at, and shown in the tree. A filter that can't be read finds nothing and is named beside the field. `Esc` empties the filter.

## Undo a move to the Trash

`⌘⌫` and the list of marks both move to the Trash without asking, on the understanding that the Trash is not the end. From Wizzzee it was: nothing could bring an item back.

`⌘Z`, **Edit ▸ Undo**, and an **Undo** button in the status bar now put back what the last move to the Trash moved — on disk, and in the tree, selected and with the marks it left with.

- It is the last move only, and only until something else is removed, the folder is scanned again, or the Trash is emptied.
- Something whose place has been taken in the meantime stays in the Trash and is named, and the rest come back.
- Marks come back too: the item's own, and for a folder those on what was inside it.

The status bar also says what Wizzzee has moved to the Trash that is still there: `In the Trash 22.4 GB`. Those bytes have left the totals and not the disk, which is why **Scanned** fell and **Volume Free** did not. That figure is what emptying the Trash frees, and it goes within a few seconds of the Trash being emptied.

## A rescan keeps your place

A scan threw the tree away, and with it which folders were open, where the map was zoomed to, what was selected, and every mark. `⌘R` is one keypress, and it emptied a list of marks that had taken ten minutes to gather.

A scan of the folder already on show now puts back what is still there: the same folders open, the map zoomed to the same folder, the same selection, the same marks, the same type in focus. A mark whose item has gone, or has been replaced by another of the same name, is counted beside "Scan complete" — `1 marked item no longer there` — so a shorter list is not taken for the whole of it. Stopping a rescan part-way does not lose them: the next scan of that folder puts them back. A scan of somewhere else starts afresh.

Between launches, Wizzzee now remembers **Size** or **On Disk**, and the volume or folder last scanned.

## Getting about

- **`→` and `←` on the tree**, as in Finder's list view. `→` opens the selected folder, and on one already open steps into it; `←` shuts it, and otherwise steps out to the folder above.
- **A row that is picked is brought into view.** Show in Tree, a line in the list of marks, and a tile clicked on the treemap all scroll the tree to the row. Show in Tree used to leave the File View in front, with the row selected behind it.
- **The path above the treemap is clickable.** Each folder in it zooms back out to there.
- **`⌘1` `⌘2` `⌘3`** for Tree View, File View and About, and **`⌘O`** for Folder….
- **A scan of a whole volume shows how far it has got**, and the folder it is reading. The bar will not always reach the end: what a volume has in use includes snapshots, unreadable folders and other volumes sharing its space, none of which a scan counts.

## Also fixed

- **Return in the File View's filter started a scan**, as it did in 0.4.0: Scan is the window's default button. With `⌘F` and a search to type, Return is the key you reach for, and it emptied the list. It does nothing there now; with the keyboard anywhere else, Return scans as it did.
- **`⌘R` could start a scan from under the folder picker**, of the folder being left.
- **A folder chosen on a volume that was then renamed** was scanned at the path it no longer had.

## Keys

| Key | What it does |
| --- | --- |
| `⌘Y` | Quick Look at the selected item, or shut it |
| `⌘F` | Search: go to the File View's filter |
| `⌘Z` | Undo the last move to the Trash |
| `→` `←` | Open or shut the selected folder; again, step into it or out of it |
| `⌘1` `⌘2` `⌘3` | Tree View, File View, About |
| `⌘O` | Choose a folder to scan |

## Limits

- Undo is for the Trash. **Delete Permanently** is still permanent.
- Putting something back never replaces what is at its old place. On APFS and Mac OS Extended that is a single step that fails if anything is there. A volume that has no such step — exFAT is one — is looked at first and then moved to, which leaves an instant in which something newly created there would be replaced.
- `In the Trash` is worked out from what left the totals, and hard links make that an estimate in one case: two names of one file, each inside a different folder, both folders trashed, and then one of the folders deleted from the Trash on its own. The line can then read low by that file.
- Quick Look asks the disk whether a file is online only when you ask for it with `⌘Y` or the menu. Moving the selection with the panel already open goes by what the scan saw, so a file sent back to the cloud since the scan can be downloaded that way.
- The treemap dims a folder drawn as a single tile whatever is inside it: a folder is no one type.
- In the search, a folder's age is its own modification date, which changes when something is added to or removed from it — not the age of what it holds.

## Installing

Download `Wizzzee-0.5.0-macos-universal.zip` below, unzip it, and move `Wizzzee.app` to Applications, replacing the old one.

- **First launch.** The app is not notarized, so macOS blocks it the first time. Open it once, dismiss the warning, then go to **System Settings → Privacy & Security** and click **Open Anyway**. macOS asks only once.
- **Full Disk Access has to be granted again.** macOS ties that permission to the exact build, so the grant from an earlier version does not carry over. In **System Settings → Privacy & Security → Full Disk Access**, remove the old Wizzzee entry and add the new app. Without it, Mail, Messages, Safari and other users' folders are skipped and the totals read low.

It runs on macOS 14 or newer, on Apple silicon and Intel.

## Internal

**Search** is one walk of the tree, as the list of largest files was. With nothing typed it still is that list, and a file too small to make it is passed over without a look. With something typed every file and folder is held up to it, because how many matched and what they come to is half of what was asked. A word asked of the path is not looked for in a path built per file: where it can be is worked out once per folder — all of it in the folder's part, or its last slash on the slash between the folder and the name.

**Undo** is the removal run backwards: the file goes back into the slot it left, the folder back under its parent, the totals back up the chain. What makes it more than that is hard links. Taking a name out can have handed its bytes to another name of the same file, so nothing is remembered about which name carried them: each one coming back is told which it is from the tree as it then stands. On disk, what goes into the Trash is taken down as what it is, with the folder it came out of, and coming back is a rename that fails if anything is there — never a copy.

**A rescan's place** is kept as paths, taken before the old tree is let go and looked up in the new one. Nothing that points into one tree means anything in the next.

This release is seven changes. Each went through the same two checks before it was merged.

A model drove the built app through each change by hand, on a throwaway disk image, with every removal checked on disk. That found three things no test had: **Show in Tree**, from the File View, selected its row behind a tab that had not moved and left it off screen; the line for what is in the Trash did not notice the Trash being emptied; and the Edit menu's item reads **Undo**, not "Undo Move to Trash".

A second model reviewed each one, in two or three passes, and every finding was checked against the code before anything was changed — thirty-two findings in all, of which twenty-nine were acted on and three were looked into and left, each with the reason written down. Among those that were real: Quick Look opened from the right-click menu showed one file beside a highlight on another, and `⌘⌫` removed the one that was not being looked at; undo knew what it had put in the Trash only by its name there, and names there are used again; and a removal on a volume with no Trash was recorded as having gone to the folder the app was started in.

The build check caught two more: a test written in a way the release toolchain gives up on, and an older test that waited one turn of the run loop for something that now has more queued ahead of it.

Then the release was read whole — the difference from 0.4.0, as one piece — by three models, for what the seven changes do to each other, which no review of one of them could see. None found a way to remove or overwrite the wrong file, or a total that comes out wrong. Between them they raised nineteen things; seventeen were acted on and two were left with the reason written down. The one that mattered most a reading could not settle, and a keypress in the built app did: Return in the filter started a scan. The others were places where the screen and the keys had come apart — rows of the search before still answering `⌘⌫` while the next was being found — or where Undo and the line for the Trash had drifted from what was in it. Every fix a test can reach has a check that fails without it, and that was tried: each was taken out in turn and the self-test run. Two cannot be reached that way — a key in a text field, and a key under the folder picker — and the first of those was pressed in the built app. The fixes were then reviewed like any other change, over three passes: five more findings, four acted on. One of those was a mark on a *folder*, which the first fix had left going back on whatever folder had the name. Last, the two reviewers who had not seen the fixes were asked whether their own findings were settled and what the fixes had brought in. They were, but for a corner of one that is now among the limits above; seven more small things came of it, three acted on and four left.

The self-test grew from 402 checks to 714. After every undo it holds the tree to a fresh scan of the disk; a few of the new ones put the real window together off screen and ask its tables what they are showing.
