# Wizzzee 0.3.2

Wizzzee is a disk space analyzer for macOS in the shape of [WizTree](https://diskanalyzer.com/): a folder tree with sizes, a list of the biggest files, and a colored treemap you can click into. It scans a full startup disk — around 3.9 million files — in roughly 15 seconds.

**Upgrade to this one.** 0.3.1 could permanently delete files other than the ones its confirmation named, and one route to deleting a whole home folder was still open. Both are closed here, along with a crash and a run of wrong numbers. Everything below came out of a second full review of the app.

Coming from 0.2.x? [0.3.0](https://github.com/SaiBarathR/wizzzee/releases/tag/v0.3.0) is worth reading as well: it fixed a bug that let Wizzzee delete the folder you had just scanned.

## A delete could land on something you didn't pick

Three separate ways, all closed.

**A confirmation could be answered about different files.** While one delete was still running, the header's **Delete…** button for a multiple selection stayed live. If you raised its confirmation then, the running delete finished underneath it and renumbered the files in that folder — and confirming deleted whatever had moved into those positions, not the files the dialog listed. A pending confirmation is now dismissed the moment the tree changes, and those buttons are disabled while a delete runs.

**A home folder could be deleted through the data volume.** 0.3.0 made Wizzzee refuse to delete a whole volume or a home folder. But a scan of `/System/Volumes/Data` shows your home folder as `/System/Volumes/Data/Users/you`, and the check only recognised `/Users/you`. **Delete Permanently…** on that row went ahead. That path is now treated as the folder it is, and the data volume's own top row as the volume it is.

**A scan could be started in the middle of a delete.** **Scan**, **Folder…** and ⌘R all still worked while a delete was running. The delete then finished against the new scan instead of the one it was started on: wrong totals at best, a crash at worst. They are disabled until the delete finishes.

## Deleting a folder got hard links wrong

Some files have more than one name. A hard link isn't a copy — it is a second name for the same bytes, and deleting one name frees nothing while another still exists. macOS uses them heavily in developer caches and package stores.

0.3.1 taught Wizzzee to handle this when you delete a single file. Deleting the **folder** that file was in walked straight past it:

- The file's size vanished from the totals, though it was still on disk under its other name — which went on showing as costing nothing.
- The "Hard links" figure in the status bar never moved.

Folders now get the same treatment as files: the surviving name takes the size over.

**The delete confirmation promised space a folder couldn't give back.** It quoted the folder's whole size, including files in it that have another name somewhere else — so it could say "50 GB will be reclaimed" for a delete that freed nothing. The figure now leaves those files out, and says so. That includes files whose other name is outside the area you scanned. A folder that holds *every* name of a file still counts it in full, since deleting the folder really does free it.

**The Trash still counts as a name.** Moving one name of a hard-linked file to the Trash doesn't remove it; the Trash holds it until it is emptied. Wizzzee treated the remaining name as the last one and promised its space back. It now goes on counting that file as shared, which is the truth until the Trash is emptied and you rescan.

## Two crashes around the treemap

- **Rescanning while zoomed in.** Zoom into a folder and press ⌘R before the map had finished redrawing, and the redraw could read folders the rescan had already thrown away.
- **Clicking the map just after a delete.** For a moment after a delete, the map still shows the old tiles. Clicking one that belonged to the folder you had just removed selected something that no longer existed, and the app could crash a moment later. The map now ignores clicks until it shows the folder as it is.

## The tables

- **"% of Parent" sorted by the wrong size.** The column shows space on disk by default, but sorting by it ranked rows by logical size. A sparse disk image could sort above a file that plainly took more of the folder, and the percentages read out of order.
- **The File View filter couldn't find accented names.** A file called `Élan.MOV` could not be found by typing `Élan` or `élan`, and an accent typed into the filter matched almost nothing: macOS usually stores `é` in a file name as an `e` plus an accent mark, and the keyboard types it as one character. Both now match, in either case. The filter is still accent-*sensitive* — `resume` does not find `résumé`.
- **Typing in the filter on a big scan could lag and show the wrong rows.** Each change to the filter started a pass over the whole scan and let the previous one run to the end first. The passes queued up, and an out-of-date one could land and stop the spinner while the real answer was still on its way. A pass that has been overtaken now stops, and only the newest one is shown.

## Volume figures stay current

- **Volume Used and Volume Free follow a delete.** They were read once when the scan finished, so after deleting 80 GB the folder totals dropped and the header went on showing the old free space until the next scan.
- **The volume picker follows your disks.** The list was read once at launch. A disk plugged in afterwards never appeared, and an ejected one stayed listed. Renaming the selected disk keeps it selected.

## Installing

Download `Wizzzee-0.3.2-macos-universal.zip` below, unzip it, and move `Wizzzee.app` to Applications, replacing the old one.

- **First launch.** The app is not notarized, so macOS blocks it the first time. Open it once, dismiss the warning, then go to **System Settings → Privacy & Security** and click **Open Anyway**. macOS asks only once.
- **Full Disk Access has to be granted again.** macOS ties that permission to the exact build, so the grant from 0.3.1 does not carry over. In **System Settings → Privacy & Security → Full Disk Access**, remove the old Wizzzee entry and add the new app. Without it, Mail, Messages, Safari and other users' folders are skipped and the totals read low.

It runs on macOS 14 or newer, on Apple silicon and Intel.

## Internal

This release came out of a second review of the whole codebase. It reported ten problems; each was reproduced with a failing check before being fixed, and all ten turned out to be real.

Every fix was then reviewed by a second model before it was merged. That found five more problems — in the fixes themselves, including a file filter that for a while could not find `Straße.txt` by its own name, and a check that would have failed on a busy machine for no reason. All five were corrected before anything shipped. The combined result was then reviewed once more as a whole, which is where the second treemap crash above came from; it had been present since 0.3.1.

The self-test that guards the scanner and the delete paths grew from 148 checks to 235, and runs clean under a thread sanitizer.

The scanner itself was not touched, so scan speed is unchanged. Plain filters in the File View take one extra comparison per file and measure 1–3% slower — under a tenth of a millisecond on a 385,000-file folder.
