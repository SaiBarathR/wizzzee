# Wizzzee 0.4.0

Wizzzee is a disk space analyzer for macOS in the shape of [WizTree](https://diskanalyzer.com/): a folder tree with sizes, a list of the biggest files, and a colored treemap you can click into. It scans a full startup disk — around 3.9 million files — in roughly 15 seconds.

**This release is about removing things.** You can now pick items out of different folders and remove them together, with a list of what you picked and what it adds up to. A delete shows how far it has got and can be stopped part-way. Taking a row out no longer redraws the whole table. And `⌘⌫` works.

## Mark things in different folders, then remove them together

Until now the only way to act on several items was the table's own selection. It could hold rows from different folders, but only for as long as every one of those folders stayed open and you clicked nothing else: one plain click, a click on the treemap, collapsing a folder or switching tabs, and it was gone. The only look at what you were about to remove was six names in an alert.

Every row in the Tree View and the File View now starts with a checkbox. Ticking it **marks** the row for removal. A mark is not the selection — it stays where you put it while you open and close folders, sort, filter and switch tabs, so you can go through a scan gathering things up and deal with them at the end.

There are four other ways to put a mark on, all of which take it off again too:

- **Space**, on whatever rows are selected
- **Mark for Removal** in the right-click menu
- **File ▸ Mark for Removal**, `⇧⌘M`
- **`⌘`-click** on a tile in the treemap

Marking a folder marks everything in it: what is inside shows a greyed tick that you can't change on its own, and if you had marked some of its contents separately, the folder's mark replaces them. A folder with only some of its contents marked shows a dash. So nothing is ever counted twice.

As soon as anything is marked, the status bar says how many items and how much space: `3 marked • 22.0 MB`. Click that to open the list. It sits above the status bar on every tab and shows each marked item with the folder it is in, how many items it holds, and its size, with the total at the top. From there:

- the **ⓧ** at the start of a row takes that mark off — nothing is removed
- clicking a row opens its folder in the tree and selects it, so you can see where it is
- **Clear** takes every mark off
- **Move to Trash** moves all of them, straight away
- **Delete…** asks first, then deletes all of them for good

On the treemap, marked tiles are hatched, so you can see what is about to go as a share of the disk.

A few things worth knowing:

- The total is always space on disk, whichever of **Size** and **On Disk** the tables are showing. It sits beside a button that removes without asking again, and a sparse disk image's length is not what deleting it gives back.
- A hard link whose data has another name elsewhere counts for nothing in the total, because removing it frees nothing.
- What can't be removed can't be marked: the folder you scanned, a whole volume, a home folder, anything on the sealed system volume.
- A mark on something that turned out not to be removable stays on, so the list never empties as though the job were done. A rescan clears all marks.
- Marks can't be changed while a removal is running. It took them as they stood when it started.

## A delete shows how far it has got, and can be stopped

Since 0.3.0 a delete has run in the background with a progress bar and a Stop button. But the bar counted whole items, so deleting one folder — which is the usual case — was a bar that sat at nothing until it was all over, and Stop did nothing until then either.

The status bar now counts the files and folders actually removed, against what the scan found, with the space beside it:

> Removing node_modules   41,200 of 118,000 items  •  2.1 GB of 6.4 GB

**Stop** takes effect at the next file. What has gone is gone; what is left stays in the tree, and Wizzzee reads it back from the disk so every total is what is really there. In testing, a delete of 800,000 files was stopped part-way and the app's counts afterwards matched the disk exactly.

Two things that used to end a delete no longer do:

- **A file that can't be removed costs only itself.** One locked file used to stop the whole folder at that point, with everything after it left behind and the tree still showing the folder as it had been. Now everything else goes, the alert names the file that stayed and why, and the tree shows what is left.
- **Very deep folders can be deleted.** macOS limits a path to 1,024 bytes, and a folder whose contents ran deeper than that could not be deleted at all — the attempt failed outright. It can now.

Moving to the Trash is a single step per item, so its progress still counts items.

## Removing a row no longer redraws the table

Every delete used to redraw the whole table, empty the File View and refill it a moment later, and drop whatever you had selected.

Now the row goes and the others stay where they are, with the same folders open and the table scrolled to the same place. If the row you deleted was the one selected, the selection moves to whatever took its place — the next row, or the one before it if that was the last, or the folder itself once it is empty. So you can work down a list with the keyboard.

While a removal that takes more than a moment is running, the rows on their way out are dimmed, with a spinner on the one you asked for.

One thing does still move. The tables are sorted by size, so a folder that shrinks below its neighbour drops down the list when you delete something in it.

## `⌘⌫` and `⌥⌘⌫`

Removing an item was only ever in the right-click menu; nothing answered the keyboard. The File menu now has both, on the keys Finder uses:

| Key | What it does |
| --- | --- |
| `⌘⌫` | Moves the selection to the Trash, without asking |
| `⌥⌘⌫` | Deletes the selection permanently, after the usual confirmation |

Because `⌘⌫` asks nothing, both keys act only on a selection you can see: a row in the tab in front, or the tile outlined on the treemap. A row you selected and then hid by collapsing its folder, or something selected in a different tab, is left alone.

`⌘⌫` in the File View's filter still deletes the text you typed. And pressing either key on something that can't be removed — the folder you scanned is selected the moment a scan finishes — tells you why instead of doing nothing.

## Smaller changes

- **A button for the treemap.** The right-hand end of the status bar has a button that shows and hides the treemap, the same as `⌘T` and **View ▸ Hide Treemap**.
- **Files of the same size keep their order.** The File View lists the thousand largest files, and which of a run of equal-sized files made the list — and in what order — used to change whenever anything in the scan did. In a folder of small files, where most are one of a few sizes, the list reshuffled on every delete.
- `Wizzzee --uishot` has a `--mark N` option, for rendering a picture of the marks without clicking.

## Limits

- A file or folder whose **own** path is longer than 1,024 bytes still can't be deleted on its own; you get an alert saying the name is too long. Deleting the folder above it removes it.
- `⌘`-click on a treemap tile was checked by the self-test but not by clicking, because the tool used to click through the app can't hold a modifier key.

## Installing

Download `Wizzzee-0.4.0-macos-universal.zip` below, unzip it, and move `Wizzzee.app` to Applications, replacing the old one.

- **First launch.** The app is not notarized, so macOS blocks it the first time. Open it once, dismiss the warning, then go to **System Settings → Privacy & Security** and click **Open Anyway**. macOS asks only once.
- **Full Disk Access has to be granted again.** macOS ties that permission to the exact build, so the grant from an earlier version does not carry over. In **System Settings → Privacy & Security → Full Disk Access**, remove the old Wizzzee entry and add the new app. Without it, Mail, Messages, Safari and other users' folders are skipped and the totals read low.

It runs on macOS 14 or newer, on Apple silicon and Intel.

## Internal

Permanent deletes now call `removefile(3)` directly. That is the routine underneath `FileManager.removeItem`, which keeps what it learns on the way to itself; called directly it reports each entry as it goes, which is where both the progress and the Stop come from. A symbolic link is removed and never followed, and nothing on another volume is touched.

The flicker had one cause. A file was named by its position in its folder's list, and deleting one took its entry out, renumbering every file after it — so the table was handed rows it had never seen. A deleted file now keeps its place in the list, marked as gone, and everything that outlived the delete goes on naming what it named. That is also what lets marks and the selection survive one.

Scan time and memory are unchanged: 9.8–10.1 seconds and 411–413 MB on a home folder of 2.8 million files, in three runs each of 0.3.4 and this build.

This release is three changes, and each went through the same two checks before it was merged.

A second model reviewed each one, in up to four passes, and every finding was checked against the code before anything was changed. Among those that were real: `⌘⌫` could reach an item that was selected but was neither a row on screen nor outlined on the treemap; after a part-finished delete in a very deep folder, files that had gone were still listed; and marks could be changed while a removal that had already taken them was running, so the list could stop showing something still on its way out. Four findings were looked into and not acted on, each with the reason written down.

Then a model drove the built app through each change by hand, on throwaway disk images, with every removal checked on disk. That found three things no test had: `⌘⌫` did nothing on a File View row picked straight after using the filter; equal-sized files changed places after a delete; and 60,000 files vanish too quickly to watch a progress bar, so that part was done again on 800,000.

The build check caught one more. The delete routine compiled on the machine it was written on and not with the older toolchain releases are built with, so it would have failed at exactly this step.

The self-test grew from 297 checks to 402. The new ones hold a removal to the disk and not to what it says about itself: a count of the folder taken beforehand against the count reported; a locked file left behind with everything else gone; a folder deeper than the path limit; a stop part-way, compared against a fresh scan of what is left.
