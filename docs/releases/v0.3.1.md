# Wizzzee 0.3.1

Wizzzee is a disk space analyzer for macOS in the shape of [WizTree](https://diskanalyzer.com/): a folder tree with sizes, a list of the biggest files, and a colored treemap you can click into. It scans a full startup disk — around 3.9 million files — in roughly 15 seconds.

A follow-up to [0.3.0](https://github.com/SaiBarathR/wizzzee/releases/tag/v0.3.0), which is the one worth reading if you are coming from 0.2.x — it fixed a bug that let Wizzzee delete the folder you had just scanned. This release finishes a piece of accounting that 0.3.0 left half-done, and takes the last of the treemap's work off the main thread.

## Deleting a hard-linked file no longer loses its size

Some files have more than one name. A hard link isn't a copy or an alias — it is a second name for the same bytes, and macOS uses them heavily for Time Machine snapshots and inside developer caches. Deleting one name doesn't free anything while another name is still there.

Wizzzee counts those bytes once, under whichever name it reaches first, and shows the other names as costing nothing. That is the right way to total a disk. But when you deleted **the name it happened to count under**, the bytes vanished from the totals too — even though they were still on disk under the other name.

The effect was a folder that reported less than it really held, and a scan total that quietly drifted below what the disk said, until you rescanned.

Now the other name takes over. Delete one of a pair and its size moves to whichever name is left, so the folder totals keep matching the disk. Delete the last name and the space finally comes off, as it should.

Two related fixes come with it:

- **A file left as the only name of its data can promise its space again.** Previously it stayed marked as sharing storage, so the delete confirmation offered "0 bytes will be reclaimed" for a file the tree had just credited with its full size.
- **The "Hard links" figure in the status bar** — the space that would be double-counted if every name were counted in full — now falls as those names are removed, instead of describing a state that no longer exists.

If a hard-linked file's other name lives outside the folder you scanned, nothing changes: those bytes really do leave the scanned tree when the name does, and the total drops as before.

## The treemap no longer builds itself on the main thread

Laying the treemap out — working out where every tile goes — ran on the same thread that draws the window, so the app stopped responding for as long as it took. It happens more often than it sounds: on every zoom, every switch between Size and On Disk, every change to the tree, and repeatedly while you drag the divider above it.

For a typical folder that is around 20 milliseconds a time, which is short enough that you would not name it but long enough to take the edge off dragging. A folder with a very large number of entries in a single directory is considerably worse.

It now happens in the background, along with the drawing that was already there. The two arrive together, so the outlines and folder labels always match the picture underneath them.

## Internal

The treemap change is the last item from the code review that prompted this series, and it was done without the refactor that review proposed. Wizzzee already had a mechanism for reading the scanned tree in the background safely — the file list uses it — so the treemap now uses one too, and deleting a folder waits for any layout in flight before it unlinks anything. That is checked by a test that leaves two dozen layouts running and deletes a folder underneath them, run under a thread sanitizer that reports the fault when the safeguard is removed.

The hard-link fix needed the inode number stored per file, which the earlier write-up had ruled out as costing about 32 MB of memory on a full-disk scan. That turned out to be wrong: the per-file record had unused padding, and the link count next to it was a 32-bit field whose value is only ever compared against one. Narrowing that to a single byte paid for the inode exactly — the record is 56 bytes, the same as in 0.3.0 — and a check now enforces that, so it can't quietly grow later.

Scan speed is unchanged: a 427,000-file folder still scans in about 6 seconds.

The self-test that guards the scanner and the delete paths grew from 125 checks to 148 — a hard-linked pair split across two folders, the mirror case of deleting the uncounted name first, a link whose partner sits outside the scan, and the layout-during-delete check described above.
