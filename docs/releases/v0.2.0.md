# Wizzzee 0.2.0

> [!IMPORTANT]
> **Two bugs in this version give wrong answers without saying so.** Scanning a folder that is itself a symlink — `/tmp`, `/etc`, `/var`, or any `/private/…` spelling of them — reports zero bytes and zero files instead of the real total, alongside "Scan complete". And for a short window after deleting a file, the File View can reveal in Finder, or delete, a *different* file than the one clicked. Both are fixed in [0.2.3](https://github.com/SaiBarathR/wizzzee/releases/tag/v0.2.3); prefer it over this release.

Wizzzee is a disk space analyzer for macOS in the shape of
[WizTree](https://diskanalyzer.com/): a folder tree with sizes, a list of the
biggest files, and a colored treemap you can click into. It scans a full startup
disk — around 3.9 million files — in roughly 15 seconds.

This release adds multi-item deletion, lets the treemap be hidden, and fixes a
crash that could follow any delete made from the context menu.

## Deleting many items at once

Both tables now take a multiple selection, using the same gestures as Finder:
⌘-click to toggle, ⇧-click for a range, ⇧-arrow to extend.

- **Bulk Move to Trash and Delete Permanently.** Available from the right-click
  menu, and — once more than one item is selected — from buttons in the header,
  where the version line sits. They read *Move 12 to Trash* and *Delete 12…* so
  the count is never in doubt.
- **The header shows what the selection costs.** For a multiple selection it
  reports the item count and the space that deleting it would actually reclaim,
  counting a folder's contents once rather than once per nested selection.
- **A folder selected together with something inside it** collapses to the
  folder. Deleting it takes the contents with it, so acting on both would fail on
  a path that no longer exists and subtract the same bytes twice.
- **Partial failures are reported honestly.** Whatever succeeded is applied, and
  the alert says `N of M items couldn't be removed` — a batch that half worked
  can't be mistaken for one that didn't.
- **Anything on the sealed system volume disables the bulk buttons outright,**
  rather than deleting the part of the selection that happens to be allowed.
  System Integrity Protection makes those paths read-only for everyone,
  administrators included.

Sizes still update all the way up the tree immediately, with no rescan.

## Show or hide the treemap

**View ▸ Hide Treemap** (`⌘T`) gives the whole Tree View tab to the folder table
and the file-type legend, for when a long folder list is what you are reading.
The menu item becomes **Show Treemap** to bring it back, at the same zoom it was
left at. The two treemap zoom commands are disabled while it is hidden.

## Fixes

- **Fixed a crash after deleting from the context menu.** Removing a file
  renumbers its siblings, and SwiftUI keeps a context menu's content alive and
  re-runs it once the confirmation sheet closes — by then the entry it referred
  to had moved, and reading it trapped on an out-of-range index and took the app
  down. Every such read now degrades to an empty value, and a reference that has
  gone stale is never acted on. In particular it does not fall back to the
  containing folder, which would have aimed a delete at the parent of whatever
  was picked.
- **The window no longer offers native tabs.** The View menu had picked up macOS
  **Show Tab Bar** and **Show All Tabs**, and using either put a system tab bar
  with a `+` directly above Wizzzee's own tab strip. A native tab was just a
  second window also called "Wizzzee", stacked behind the first with nothing to
  tell the two scans apart.

## For the command line

`--uishot` gains `--no-treemap`, which renders the table-only layout. See
[docs/cli.md](https://github.com/SaiBarathR/wizzzee/blob/main/docs/cli.md).

## Reading the numbers

- **On Disk is the default.** Logical size is misleading on macOS, where sparse
  container and VM images routinely report hundreds of gigabytes they do not
  occupy. Space on disk is what deleting something gives back.
- **Base-10 units,** matching Finder and Get Info. This differs from `df -h`,
  which is base-2.
- **Hard links are counted once,** with the amount that would otherwise have been
  double-counted shown in the status bar.
- **One volume per scan.** APFS firmlinks are followed once, so `/Users` is
  counted and `/System/Volumes/Data/Users` — the same directory by another path —
  is not.
- **Totals will not exactly match `df`.** Unreadable folders, APFS snapshots and
  filesystem metadata account for the difference; the header reports how many
  folders could not be read.

## Full Disk Access

Without it, macOS hides Mail, Messages, Safari, Time Machine and other users'
home folders, and the totals read low. The header says so when it detects this.

Grant it in **System Settings → Privacy & Security → Full Disk Access → +**,
adding `Wizzzee.app`.

**Upgrading from 0.1.0:** because the app is ad-hoc signed, macOS keys the grant
to that exact binary, so 0.2.0 has to be added to Full Disk Access again. Remove
the old entry and add the new app.

## Compatibility

- Requires macOS 14 or newer.
- Apple Silicon is verified.
- The universal app contains native `arm64` and `x86_64` slices. Intel hardware
  has not been tested, so Intel support is provisional rather than verified.

## Installation

1. Download `Wizzzee-0.2.0-macos-universal.zip` and `SHA256SUMS.txt`.
2. Keep both in the same directory and run `shasum -a 256 -c SHA256SUMS.txt`.
3. Unzip and move `Wizzzee.app` to Applications.
4. Open it once and dismiss the warning, then go to **System Settings → Privacy
   & Security** and click **Open Anyway** next to the message about Wizzzee.

Wizzzee is ad-hoc signed rather than Developer ID signed or notarized, so macOS
requires this one-time Gatekeeper confirmation. On macOS 14 you can instead
Control-click the app and choose **Open** — macOS 15 removed that shortcut for
apps that are not notarized.

## Verification

After extraction:

```sh
lipo -archs "Wizzzee.app/Contents/MacOS/Wizzzee"
codesign --verify --deep --strict --verbose=2 "Wizzzee.app"
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' "Wizzzee.app/Contents/Info.plist"
```

These should report both `arm64` and `x86_64`, a valid ad-hoc signature, and
version `0.2.0`.

You can also check the build itself:

```sh
"Wizzzee.app/Contents/MacOS/Wizzzee" --selftest
```

That builds a throwaway tree with known contents and verifies the scanner and
both delete paths against ground truth — 65 checks, no permissions needed. The
count grew from 0.1.0 mostly with the batch-delete cases: that two siblings
deleted together leave the *correct* survivor, that a folder selected alongside
its own contents is removed once, and ten checks that reproduce the crash above
by capturing a reference, deleting ahead of it, and then reading it the way the
menu did.

## Known limitations

- Not notarized, so first launch needs the Gatekeeper confirmation above.
- One volume per scan; other disks and network shares are skipped.
- `/System`, `/usr`, `/bin` and `/sbin` live on the sealed system volume and
  cannot be deleted by anything, including an administrator. Wizzzee still shows
  them so the space is accounted for, and says so rather than failing with a bare
  permission error.
- Treemap visibility is not remembered between launches; each launch starts with
  it shown.
